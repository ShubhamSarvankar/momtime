# 0036. Materialising a window is one atomic repository operation

Date: 2026-09-30
Status: Accepted

## Context

`ARCHITECTURE.md` section 3.2 has the rolling window regenerated by a daily worker and again on any template edit, so two materialisation runs can overlap. Materialisation was a read followed by separate inserts: read the dates already materialised, compute the missing ones, insert them. Two overlapping runs could both compute the same missing date. The `UNIQUE(template_id, local_date)` index stopped the second row, but the insert was `INSERT OR IGNORE`, so the loser skipped the row silently.

That also hid bugs. With `OR IGNORE`, an engine that re-issued an already-materialised date looked identical to a correct one, and a test that removed the engine's `filterNot` stayed green (found by mutation check in Phase 1).

Replacing `OR IGNORE` with a plain `INSERT` without fixing the race is not safe: the loser would throw part way through its batch, and if its window differed from the winner's, the dates after the failure would never be inserted. That is a dose with no occurrence and no alarm.

## Decision

1. Materialising one template over a window is a single repository operation, `OccurrenceRepository.materialiseWindow`, in one transaction: read the existing dates, compute the missing ones through `OccurrenceMaterialiser`, allocate their `alarmSlot`s, insert them. With the read and the writes atomic, the loser of a race sees the winner's rows and `filterNot` excludes them.
2. `insertOccurrence` is a plain `INSERT`. A duplicate can now only come from a broken engine, and that fails deterministically in the test suite instead of being absorbed in production.
3. If any insert throws, the whole batch rolls back, including its `alarmSlot` allocations. No partial batch survives and no slot is burned.
4. Correctness does not depend on how workers are scheduled. An edit-triggered run may never go through `WorkManager`. Unique work in Phase 2 is an efficiency measure only (it avoids redundant runs) and is tracked as an optimisation in `IMPLEMENTATION_PLAN.md` Open Items.

This is a query change, not a schema change: the unique indexes already exist, so there is no migration.

## Driver findings

Whether a transaction actually serialises a read followed by a write depends on the driver. `BEGIN` (deferred) across two connections does not serialise; a single connection or `BEGIN IMMEDIATE` does. Read from source, SQLDelight 2.4.0:

| Driver | Connection model | Transaction start | Serialises read-then-write? |
|---|---|---|---|
| `JdbcSqliteDriver`, in-memory (used by `jvmTest`) | One shared connection (`StaticConnectionManager`, `JdbcSqliteDriver.kt`, selected for empty, `:memory:` and `mode=memory` URLs) | `BEGIN TRANSACTION`, deferred | Yes, trivially: there is only one connection. It cannot express a race at all. |
| `JdbcSqliteDriver`, file URL | One connection per thread (`ThreadedConnectionManager`) | `BEGIN TRANSACTION`, deferred | No. Observed in `MaterialiseAtomicityTest`: while run A holds its read lock, run B on another connection fails with `SQLITE_BUSY`. It is refused loudly rather than silently interleaved, but it does not wait its turn. |
| `AndroidSqliteDriver` (the app, Phase 2) | The framework `SupportSQLiteDatabase` | `database.beginTransactionNonExclusive()` (`AndroidSqliteDriver.kt`, `newTransaction`), which the framework implements as `SQLiteSession.TRANSACTION_MODE_IMMEDIATE` (AOSP `SQLiteDatabase.java`, `beginTransactionNonExclusive` calling `beginTransaction(listener, false)`) | Yes: `BEGIN IMMEDIATE` takes the write lock at the start, so a second writer waits. |

Limits of this evidence. The Android claim rests on reading the driver source and the AOSP `main` branch; `AndroidSqliteDriver` is not yet in this repository and the behaviour has not been run. The deferred-tests table in `MANUAL_CHECKS.md` assigns that run to Phase 2. The AOSP source was not checked per API level.

## Alternatives considered

- Keep `INSERT OR IGNORE` and add telemetry when an insert is ignored (option b) — rejected. It detects a duplicate-issuing engine only after release, and an ignored insert is indistinguishable from a legitimate race loser.
- Serialise materialisation through `WorkManager` unique work — rejected as the correctness mechanism. It does not cover an edit-triggered run that bypasses `WorkManager`, and it ties a data invariant to a scheduler. Kept as an optimisation.
- Plain `INSERT` without a transaction — rejected. The race loser would throw mid-batch and lose later dates.
- A custom `BEGIN IMMEDIATE` JDBC driver for the tests — not built. It would test a simulation of Android rather than Android, and the test that exists does not need it.

## Consequences

- Materialisation correctness is a property of one repository operation and its test, `MaterialiseAtomicityTest`, not of worker scheduling.
- The race test forces its interleaving with latches inside the `generateId` callback the engine already takes (no production hook) and uses a zero busy timeout, so its outcome does not depend on timing. Checked by mutation: removing the transaction fails it on every run (three of three), and removing the engine's `filterNot` makes the insert throw with no partial batch left behind.
- Any future caller that inserts occurrences outside `materialiseWindow` must not assume duplicates are ignored.
