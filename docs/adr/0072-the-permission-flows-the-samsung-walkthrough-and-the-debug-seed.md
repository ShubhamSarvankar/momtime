# 0072. The permission flows, the unused app restrictions, the Samsung walkthrough and the debug seed

Date: 2026-10-05
Status: Accepted

Decided by Claude (technical review) in the PR 8 prompt: each flow and the API level it exists at, the battery flow through the general settings screen, the overlay offered only without an effective full screen intent, the unused app restrictions check and its banner, the Samsung walkthrough with deep links and fallbacks and placeholder screenshots, the flow from the ring screen, the debug seed and its release manifest check. The structure (the controller, the screens, the check's fixtures) and the placeholder component names are the implementing session's, for review. It builds on ADR 0050 (capability), ADR 0053 (`ensureArmed`) and ADR 0070 and ADR 0071 (the banner state it feeds).

## Context

Until now the app declared its permissions and resolved capability, but nothing asked her for anything, so a phone that had not granted exact alarms, full screen intent or a battery exemption stayed at Tier 1 or 2 with nothing to tell her. Phase 3's onboarding does not exist yet. A real device also has no way to put a reminder in front of a real alarm until Phase 3's schedule builder exists.

## Decision

1. **Each flow resolves capability again on return and then calls `ensureArmed`.** `SetupController.onReturn` resolves capability from the platform as it is now, builds the state the screen shows from that, and then calls `ensureArmed`, so a reminder that could not be armed through the old tier is armed through the new one at once. The screen calls it every time it resumes, which covers coming back from any settings screen and from the notification dialog. Capability is never remembered and never inferred from the version: the version says only which screen exists.
2. **The flows, and where each exists** (`PermissionFlows`): notifications, a runtime request on API 33 and above (the first time), the app's notification settings after a request or below 33; exact alarms, `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` on API 31 and 32 only (`USE_EXACT_ALARM` covers 33 and above, nothing is needed below 31); full screen intent, `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` on API 34 and above; battery, the general `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`; overlay, `ACTION_MANAGE_OVERLAY_PERMISSION`, **offered only when an effective full screen intent is not available** (it is the secondary route, never the ringing mechanism); unused app restrictions, `ACTION_AUTO_REVOKE_PERMISSIONS` on API 30 and above. A flow that is needed but has no launch at this level says so on its row and shows no button.
3. **The battery flow is the general settings screen, and `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` is not declared.** The direct request waits on the Open Items row Shubham owns (`IMPLEMENTATION_PLAN.md`: its own Play policy, as `USE_EXACT_ALARM` has), whose written fallback is this one. `verifyManifestPermissions` fails if the permission appears.
4. **Android's unused app restrictions are checked, shown in the report, and a banner state.** On API 30 and above "pause app activity if unused" can revoke an app's permissions and stop it when it has not been opened for months, and a reminder delivered by notification may not count as use. `PackageManager.isAutoRevokeWhitelisted()` and `Intent.ACTION_AUTO_REVOKE_PERMISSIONS` are framework calls from API 30, so **no `androidx.core` and no dependency was needed**. The state is read through a seam in the DI package, true (exempt), false (the restriction applies) or null (below 30), carried in the report and the export, and raises `Banner.UnusedAppRestrictions`.
5. **The Samsung walkthrough** (`SamsungStepsActivity`) covers four settings: the battery setting (Unrestricted), Sleeping apps, Deep sleeping apps, and Put unused apps to sleep. It is shown when `Build.MANUFACTURER` is Samsung, read through a seam; that is presentation only, and capability is still resolved at runtime. Each step tries its deep link (a component of Samsung's Device Care) and falls back, on `ActivityNotFoundException` or `SecurityException` (a component that is not visible, or not exported), to a general settings screen, with the step's screenshot and caption on screen and a hint that the general settings opened. **Every component name is unverified until a device check**, so each has a `MANUAL_CHECKS.md` row, and the fallback is what makes an unverified name safe. The screenshots are placeholder drawables with fixed names until Shubham supplies the Galaxy A15 ones. Captions are resources, English only (Claude (technical review)).
6. **The flow until Phase 3's onboarding exists:** the ring screen's idle state links to the permission screen, which continues to the Samsung steps on a Samsung and then to the reliability check (ADR 0069), or straight to the check elsewhere.
7. **The debug seed** is in the `debug` source set only: a launcher entry in the debug manifest and a screen that seeds, through the domain's repositories and commands, one CRITICAL test reminder three to four minutes out (an inactive template with one materialised occurrence, so the daily job never adds a second day) and three daily STANDARD reminders, then materialises and calls `ensureArmed`, so exactly one alarm is armed. It exists so that someone can test real alarms on a real device before Phase 3, and is kept past Phase 3 as a debug tool unless Phase 3 decides otherwise. **`verifyNoDebugComponents` fails the build if any component of the debug package appears in the merged release manifest**, and fails closed twice: a missing manifest, and a merged debug manifest that declares no debug component (the pattern would then be matching nothing). A self test with fixtures proves each kind of component is detected and a lookalike package and the word "debug" elsewhere are not. It is wired into `check` and into the `verify-android-structure` CI job.

## Alternatives considered

- **Declare `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` and request the exemption directly.** Not now (Shubham's Open Items row): its own Play policy.
- **Infer the walkthrough from the OS version, or from a list of known vendors.** Rejected: capability is resolved at runtime; the maker only chooses which screen to show.
- **Verified Samsung component names from memory.** Not possible: they change between One UI versions. Placeholders with fallbacks, and a device check each.
- **Real screenshots now.** Not possible without the device: Shubham supplies them.
- **A debug build type for the seed.** Rejected: a source set is simpler, and the release manifest check proves the result rather than the configuration.
- **A debug flag inside the main code.** Rejected: dead code in release is still code.

## Consequences

- `ARCHITECTURE.md` section 5.2 is updated in the same commit. `MANUAL_CHECKS.md` gets a row for each deep link (P2-34 to P2-37), for the permission flows on a device (P2-38), for the unused app restrictions (P2-39), for the boot gap (P2-40) and for the seed screen (P2-41).
- Nothing here has run on a device.
