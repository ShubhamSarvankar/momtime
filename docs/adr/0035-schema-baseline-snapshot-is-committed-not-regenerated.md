# 0035. The schema baseline snapshot is a committed file, never auto-regenerated

Date: 2026-09-30
Status: Accepted

## Context

Getting SQLDelight's `verifyMigrations` to actually register and run a `VerifyMigrationTask` took several wrong turns, worth recording so nobody repeats them. The eventual correct model: `VerifyMigrationTask` reads a baseline `.db` snapshot from the SQLDelight **source** folder (`src/commonMain/sqldelight/databases/`), applies any newer `.sqm` migrations found in source, and compares the result against what the current `.sq` files declare.

The dangerous mistake, made and caught during Phase 1: wiring `verify*Migration` to `dependsOn` the `generate*Schema` task so the baseline would "always be fresh." This makes verification a tautology — `generateSchema` re-derives the baseline from whatever the `.sq` files currently say, `verifyMigration` then compares that freshly-regenerated baseline to itself, and a schema changed with no migration file passes silently. Confirmed directly: with that wiring in place, adding an unmigrated column to `app_settings` and running `verifySqlDelightMigration` reported `BUILD SUCCESSFUL`.

## Decision

The baseline snapshot (`shared/src/commonMain/sqldelight/databases/1.db`) is a **committed artifact**, generated once via `./gradlew :shared:generateCommonMainMomTimeDatabaseSchema` and checked into git like any other source file — not a build output, not regenerated by `check` or CI. `verify*Migration` has no dependency on `generate*Schema` in this build.

Confirmed working correctly under this model: reverting to the correct baseline, then adding the same unmigrated column and running `verifyCommonMainMomTimeDatabaseMigration` **without** regenerating the snapshot, fails with an exact column-level diff (`app_settings.unauthorised_schema_drift - ADDED`). This is the real enforcement invariant 2 requires.

Regenerating the baseline is a deliberate, reviewed, manual step for the (rare) occasion a schema version is intentionally finalised and a set of prior `.sqm` files gets squashed into a new starting point — never an automatic side effect of `./gradlew check`.

## Alternatives considered

- `schemaOutputDirectory` pointed at a `build/` directory, regenerated on every run for convenience — rejected; this is the exact tautology described above, empirically confirmed to let an unmigrated schema change through undetected.
- No baseline snapshot at all, relying solely on the `.sqm` chain — not possible with this plugin version outside `deriveSchemaFromMigrations` mode, which was evaluated and rejected separately for moving all `CREATE TABLE` statements out of `.sq` files (ADR 0033's invariant-2 reasoning argues for keeping `.sq` as the readable target schema).

## Consequences

Any future schema change must come with either a new `.sqm` migration file (the normal case) or a deliberate, reviewed baseline regeneration (rare, and itself worth its own commit message explaining why). `README.md`'s test-suite table and `IMPLEMENTATION_PLAN.md` note that the snapshot is committed, so a future contributor doesn't "helpfully" add it to `.gitignore` or a regeneration step to CI.
