# 0068. A time zone change moves open occurrences, and the system passes share one queue

Date: 2026-10-04
Status: Accepted

Revised in place in the review of PR #22, before it was merged (decisions of Claude (technical review)): the command is one transaction, a terminal occurrence is immutable in full in the schema (version 5), inactive templates follow the device zone and their open occurrences move, and the single queue has a behavioural test. The first draft left the command without a transaction, left the schema guard out, and skipped inactive templates.

Decided by Claude (technical review) in the PR 6b prompt (the semantics, items 1 to 7; the single queue question and its test); the command's shape, the repository methods and the seam are the implementing session's, for review. It answers the open question of ADR 0067 (the timezone broadcast), builds on ADR 0032 (quiet hours and the budget follow the current zone), ADR 0056 (a late rung is presented quietly) and ADR 0066 (a snooze's end is an absolute instant), and changes one detail of ADR 0067 (the work's unique name). ADR 0067 is not edited.

## Context

`ARCHITECTURE.md` section 11 says to recompute instants on timezone and time change broadcasts, and golden scenario 8 is "timezone travel where the local scheduled time has already passed". Phase 1 counted scenario 8 among its 16 passing scenarios, but its test (`GoldenScenariosDbTest`) asserts only that materialisation uses the template's zone. No code recomputed an occurrence's instant for travel, so the scenario's subject was never exercised: the same failure as scenario 5's unasserted second case. It is recorded as a precedent in `CLAUDE.md`'s testing section and as a note under scenario 8 in `IMPLEMENTATION_PLAN.md`; its real test is here.

## Decision

1. **Templates follow the device zone in v1.** An 8 AM reminder means 8 AM wherever she is, as quiet hours and the interruption budget already follow her (ADR 0032). On a zone change every template's `timeZoneId`, **active or not**, becomes the new device zone, so every later materialisation uses it and a template reactivated later is already in her zone.
2. **Open occurrences move, with a clamp.** For each `PENDING` or `SNOOZED` occurrence of any template whose own zone is not the new one, let N be its local date and the template's time of day in the new zone, and C the instant of the change. The new `scheduledInstant` is `max(N, C)` (`TravelReschedule.rescheduledInstant`, pure, with C from the injected clock). Travel never makes an occurrence overdue that was not, so a dose cannot become `MISSED` purely because she flew east; flying west moves doses later, which is what she wants. An inactive template's open occurrences can still ring, so they move too. An occurrence clamped to C is due now, and the fire path decides how it is presented (ADR 0056). Rungs already fired stay consumed under the count rule; the remaining rungs follow the new instant.
3. **Terminal occurrences are untouched,** by the command and by the schema: any update to a row whose state is terminal aborts (schema version 5, below).
4. **`snoozedUntil` is not moved.** It is an absolute instant decided when she snoozed (ADR 0066). The command writes no event, so the snooze event is untouched, and the armed alarm for a snoozed occurrence is still its end.
5. **A moved occurrence keeps its id and `alarmSlot`** (and its local date and state), so the armed alarm's request code still matches and its history is unchanged. This is a decision, not a consequence of invariant 10, which governs how request codes are derived and not whether they persist.
6. **Then the window is materialised and `ensureArmed` is called**, inside the coordinator's exclusion, with `Reconcile` between them (an occurrence that moved is judged against its new instant). The pass is `TimeZonePass`; the receiver now declares `ACTION_TIMEZONE_CHANGED`. The command itself is one database transaction (below).
7. **Pinning a template to a fixed zone**, for interval sensitive medication, is not in v1. It is an alternative recorded here, not a plan item.

**What Phase 1's edit path does with pending occurrences.** There is none: Phase 1 has no template edit path. `ScheduleTemplateRepository` offers `insert` and `setActive`, `OccurrenceRepository` changes an occurrence's state and nothing else, and scenario 1's test "edits" a template by calling `setActive` and materialising the same window again (it never changes `timeOfDay`). So nothing replaces pending occurrences with new ids or slots, and decision 5 conflicts with nothing; but there was no path to reuse. The command adds two repository methods, `ScheduleTemplateRepository.updateTimeZone` and `OccurrenceRepository.reschedule` (an `UPDATE` of `scheduled_instant` and `time_zone_id` by id, never of the id, slot, date or state), and applies the clamp on this route only. Ordinary template edits, which Phase 3 will build, are not given the clamp. The terminal rule is the command's: a terminal occurrence is never passed to `reschedule` (there is no schema level guard on its instant, which would be a migration, and a guard that silently absorbed a bad update would hide the mutation that tests the rule).

**One transaction.** The command reads the templates and the open occurrences, moves the occurrences, and updates the templates' zones, through two repositories, and the whole of it runs in one database transaction (`Transactor`, over `MomTimeDatabase.transactionWithResult`; every repository call inside joins it). Without it, a materialisation run that landed between the moves and the templates' update would read the old zone and insert new dates at the wrong instants, and the idempotence guard (an occurrence already in the new zone is skipped) would then keep anything from repairing them; one of her actions completing an occurrence between the command's read and its update is the same race. ADR 0036's serialisation (the contending run waits in the framework's connection pool) makes a run entirely before the command, so the command moves what it inserted, or entirely after, using the new zone. `TimeZoneRaceTest` holds the command on a latch inside its transaction, starts a materialisation run, releases the latch, and asserts the run completed only afterwards and every date it inserted is in the new zone; removing the transaction fails it.

**The command's other properties.** It is idempotent: an occurrence already in the new zone is skipped, so a second broadcast for the same zone, with a later C, does not move a clamped occurrence again. A moved occurrence is not an event: the log records what she did and what the system did to state, and an instant recomputed from a wall clock intent is derived, like a materialised one. Because the move writes no event, the expected occurrence upload of Phase 4 must resend an occurrence that a zone change moved (a Phase 4 note in the progress file).

**A terminal occurrence is immutable in full: schema version 5.** The trigger from version 2 aborted a change of state out of a terminal state and nothing else, so nothing stopped an instant or a zone changing on a terminal row, and `reschedule` is the first path that changes instants. `ARCHITECTURE.md` section 3.2 says terminal occurrences are immutable, so the schema now says exactly that: a `BEFORE UPDATE` trigger aborts any update to a row whose OLD state is `COMPLETED`, `SKIPPED` or `MISSED`, whatever it changes and even if it changes nothing. There is no sanctioned update to a terminal row. `migrations/4.sqm` drops and recreates the trigger under the same name (`DROP TRIGGER` and `CREATE TRIGGER` work on the SQLite 3.22 floor); no data changes. `SchemaV5Test` migrates from versions 1, 2, 3 and 4 with foreign keys on, ending in `foreign_key_check`, and shows the gap (at version 4 a terminal row's instant could be changed); the Phase 1 test that iterates every state against the trigger now covers every updatable column, under the JDBC driver (`SchemaV2Test`) and the Android driver (`AndroidSchemaTest`). The earlier draft refused this guard because a guard that silently absorbed a bad update would hide the mutation that tests the rule; the trigger raises instead of absorbing, so a terminal row touched by mistake fails loudly, and the mutation that moves one now fails on the schema's abort inside the command, which is the intended reason.

**The zone is read through a seam only.** `DeviceZone` (android, in the DI package) is the one place the device's zone is read. `verifyNoClockSystem` now bans `TimeZone.currentSystemDefault()` and `java.util.TimeZone.getDefault()` outside the DI package of each module (`com.momtime.shared.di` and `com.momtime.android.di`), with fixture self tests, because a hidden zone is the same kind of input as a hidden clock: a test could not set the zone a command ran in.

**One queue for the system passes.** ADR 0067 named the unique work per event (`momtime.system.<event>`). The review asked what happens when two broadcasts arrive close together, for example boot and then a clock change. The policy was already `APPEND_OR_REPLACE` (not KEEP, which would drop a broadcast that arrived while a pass was running, a pass that may have read the clock before the change; not REPLACE, which would cancel one in progress). With one unique name per event, though, a boot pass and a clock pass were different work and could run on two threads, ordered only by the coordinator's lock. Every broadcast now appends to **one** queue, `momtime.system`, so the passes run one after another in the order the broadcasts arrived and each reads the clock and the zone as they are when it begins. A test with `WorkManager`'s real thread pool holds a pass on a latch, delivers a second broadcast, and asserts the second runs only after the first, reading the changed clock; KEEP fails it. The test also observes the passes themselves and not a queue's name: it counts how many run at once, and with one queue per event a boot pass and a clock pass overlap on the latch (the second starts while the first is held), with the single queue they never do.

## Alternatives considered

- **No clamp: move to the new zone's wall clock time.** Rejected: flying east would make an occurrence overdue, and past its grace `MISSED`, with no action of hers.
- **Move only future occurrences, regenerating pending ones.** Rejected: new ids and slots, which orphan the armed alarm and break the history of an occurrence she may already have snoozed.
- **Templates keep the zone they were set in.** Rejected for v1 by the review; it is the fixed zone alternative above, wanted only for interval sensitive medication.
- **No schema guard on a terminal row's instant.** The first draft's choice, rejected in the review: the command's own check is not the schema, and ARCHITECTURE.md says terminal occurrences are immutable. Done, as version 5.
- **Skip inactive templates.** The first draft's choice, rejected in the review: an inactive template's open occurrences can still ring, and a template reactivated later must already be in her zone.
- **Moving the occurrences and the templates in two steps.** The first draft's choice; the race above.
- **Write an event for a move.** Not now: a new event type for a derived value, and the log would grow with every journey.
