# 0067. System broadcasts are answered by one pass, and nothing rings

Date: 2026-10-04
Status: Accepted

Decided by Claude (technical review) in the PR 6 prompt (which broadcasts, that boot only enqueues unique work that dispatches `Reconcile` and calls `ensureArmed`, that boot never rings, that the receivers prefer `exported="false"`, and that the answers on updates and exported receivers be found and recorded); the receiver and worker design is the implementing session's, for review. It builds on ADR 0053 (one entry point), ADR 0056 (a late rung is presented quietly), ADR 0057 (WorkManager) and ADR 0058 (the watchdog). It corrects one premise of ADR 0058 (below); ADR 0058 is not edited.

## Decision

**One receiver, four broadcasts, one pass.** `SystemBroadcastReceiver` is declared `exported="false"` with an intent filter for exactly `BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`, `TIME_SET` (`ACTION_TIME_CHANGED`) and `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`. It maps the action to a `SystemEvent`, ignores any other action, and enqueues unique one time work for that event (`momtime.system.<event>`, `APPEND_OR_REPLACE`, so a broadcast that lands during a pass is still answered by one that began after it, and a failed one is replaced). It takes `goAsync()` and finishes when the work is written. The worker is the same for every event: it runs `AppStart.run()`, which is `Reconcile` and then `ensureArmed` inside the coordinator's exclusion, the two steps a process start and the watchdog already use. It writes no `WATCHDOG_REPAIR` (a broadcast is not evidence that anything was lost) and, on a correct state, nothing at all: `ensureArmed` re arms with identical parameters and appends `ALARM_SCHEDULED` only when the armed rung changed.

**Boot never rings.** Boot starts no ringer and no service of any kind. It is a worker that dispatches `Reconcile` (an occurrence whose grace ended while the phone was off becomes `MISSED` with `effectiveAt` at the grace expiry, silently) and calls `ensureArmed`, which arms the earliest rung that has not fired, for now if it is overdue. The alarm that fires is the alarm path, which decides how it is presented (ADR 0056): within the catch up window as policy says, beyond it and within grace a silent notice on the Quiet notices channel (ADR 0064), so a night with the phone off gives each occurrence still in grace its own silent notice and none rings. `BOOT_COMPLETED` only: `LOCKED_BOOT_COMPLETED` is not handled and nothing is direct boot aware (progress decision 10), so nothing runs before the first unlock. A test at SDK 35 and 36 shows boot starts no service.

**An update.** `MY_PACKAGE_REPLACED` runs the pass; `ensureArmed` resolves capability at its start, so capability is resolved again. **Do alarms survive an update?** In AOSP they do, at every release from android-10 to android-16 (read from `AlarmManagerService` at the release tags): on `ACTION_PACKAGE_REMOVED` with `EXTRA_REPLACING` the service returns without removing the app's alarms ("This package is being updated; don't kill its alarms"), and only a package restart (a real force stop) or a real removal removes them. The activity manager does not cancel the app's `PendingIntent`s on a replace either: it force stops the package with `uninstalling` false (`fullUninstall = removed && !replacing`), and pending intents are removed only when uninstalling. From Android 13 the alarm service also handles `ACTION_PACKAGE_ADDED` with `EXTRA_REPLACING` by removing an app's exact alarms if it lost the permission to set them on update (`CHECK_EXACT_ALARM_PERMISSION_ON_UPDATE`). **ADR 0058 said an update clears the app's alarms; that was wrong for AOSP,** and the premise of its version code evidence (`APP_UPDATED`) was therefore a false positive on a platform that keeps them: the watchdog would write `WATCHDOG_REPAIR` for an alarm that was never lost. Two things keep that from mattering. The pass above runs on `MY_PACKAGE_REPLACED` and re arms with the new version code in the armed record, so the watchdog that follows finds the versions equal and no evidence. And the version code evidence stays as a net for a platform or an OEM that does clear alarms, and for an update whose broadcast was missed; it is not removed. `ensureArmed` is correct either way, and a test shows both: an alarm the update cleared is armed again, and an alarm it kept is left exactly as it was with nothing written. What an OEM does on a real update is not in AOSP (`MANUAL_CHECKS.md` P2-27).

**The clock.** `ACTION_TIME_CHANGED` runs the pass, which re arms the rung the domain says is next. Selection is the count of fired rungs and never a comparison of an instant with the clock (golden scenario 14): a clock set backward cannot bring a fired rung back, because nothing compares, and the scheduler arms `max(rung, now)`, never an instant in the past, so there is no negative delay. A rung that was armed for now before the clock moved back is re armed at its own instant, ahead of the new time, and a rung that becomes overdue when the clock moves forward is armed for now, with the fire path deciding its presentation. Scenario 14 is tested by name, through the broadcast, and both mutations that remove the broadcast's effect fail it.

**A grant of exact alarm access.** `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` is sent on a grant and never on a revocation; here it runs the same pass, and `ensureArmed` resolving capability again is what upgrades an inexact alarm to an exact one, replacing it in place (same slot, same rung, same trigger time). It is used only for that. A revocation is never learned from a broadcast: capability is resolved again at the start of every pass, which is how the watchdog finds one (decision d of Step 1; golden scenario 3).

**Are these broadcasts delivered to a receiver declared `exported="false"`? Yes.** The platform's component check lets the root and system uids reach unexported components (`ActivityManager.checkComponentPermission`, through `canAccessUnexportedComponents`: `appId == ROOT_UID || appId == SYSTEM_UID`, read at android-10, android-14 and android-16), and each of these broadcasts is sent by the system server (the package manager for `MY_PACKAGE_REPLACED`, the activity manager for `BOOT_COMPLETED`, the alarm service for `TIME_SET` and the permission change). WorkManager 2.12.0 ships its own boot receiver the same way (`RescheduleReceiver`, `exported="false"`, `BOOT_COMPLETED`, in the merged manifest). So every receiver here is `exported="false"`, none is exported, and there is no exported receiver for a test to attack: instead the receiver acts only on the four actions and ignores everything else (a test sends other actions, including `LOCKED_BOOT_COMPLETED` and the timezone broadcast, with a positive control), and a manifest test pins the exported flag and the exact action list. That a real phone delivers them to an unexported receiver is `MANUAL_CHECKS.md` P2-26 to P2-29.

**The timezone broadcast is not handled, and why.** `ACTION_TIMEZONE_CHANGED` should dispatch a Phase 1 command that recomputes pending and future occurrences' instants for travel (golden scenario 8, `ARCHITECTURE.md` section 11), leaving terminal occurrences untouched, and then call `ensureArmed`. Phase 1 defined no such command: scenario 8's test shows only that materialisation uses the template's zone, and `OccurrenceMaterialiser` is the only code that turns a wall clock intent into an instant. What the command should do is open (does a template's zone follow the device or stay where it was set; which occurrences move; what happens to one already materialised for a date that has passed in the new zone), and the prompt says not to invent it, so the receiver does not declare the broadcast. The pass would be correct without the command, because `ensureArmed` arms absolute instants and `Reconcile` reads the occurrence's own zone, but it would leave the instants as materialised, which is the part that is undecided. This is the one open item of PR 6.

## Alternatives considered

- **A receiver per broadcast.** Rejected: five classes doing one thing, and five manifest entries to pin.
- **Do the work in the receiver on an executor, as the alarm receiver does.** Rejected: the alarm receiver must be fast and has the fire path's exclusion; a system broadcast has no deadline, and work that WorkManager owns survives the process being killed after the broadcast.
- **An exported receiver with a permission.** Not needed: the system uid reaches an unexported receiver.
- **Remove the version code evidence now that updates keep alarms.** Rejected: it is the net for a platform that clears them, and the broadcast pass already keeps it from firing falsely on AOSP.
- **Ring a late rung from boot.** Forbidden: boot never rings (CLAUDE.md; Android 15).

## Evidence

`SystemBroadcastTest` (boot work and its unique name, `MISSED` after boot, an overdue rung armed for now with no ringer and no service, a night with the phone off giving each occurrence a silent notice, boot starting no service at SDK 35 and 36, scenario 14 backward and forward and a no op clock change, an update that cleared and one that kept the alarm, a grant upgrading out of Tier 1 and a stray grant not, unexpected actions enqueueing nothing) and `SystemManifestTest` (not exported, not direct boot aware, the exact actions). Mutations are in `phase-2-traceability.md`. Nothing here sent a real broadcast to a real phone: P2-26 to P2-30.
